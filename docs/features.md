# 功能详述

## 选股模式（左视图双 Tab）

**v4.5 起左视图改为双 Tab：AI竞价 + AI 预测**（原"盘中实时"模式因基本无人使用，9/1 起从首页移除；store 的 spot 代码与 PoolView/自选股页保留引用，仅左视图入口停用）。**v4.8（9/5）tab 更名「竞价」→「AI竞价」**（选中态红色高亮，区别于 AI预测）。

| 维度 | 竞价选股 (auction) | AI 预测 (aipick，嵌入) |
|---|---|---|
| 时段 | 9:15-9:31 竞价锁定 | 9:27 预测出榜后全天 |
| 数据 | 竞价字段(f615/f616) + 昨日成交额 | XGBoost 涨停概率 Top 榜 |
| 评分 | 竞价五因子(涨幅34/换手32/**异动17**/市值11/昨涨6) | ai_prob 涨停率 |
| 筛选 | 竞价条件（剔除ST/停牌、剔除昨日涨停、竞价涨幅≤7%、**流通市值区间**、股价、竞价金额、**分数≥50分**） | 市值/竞价金额/涨幅/涨停率≥50%（前端规则条可调） |

> **v4.11.19 筛选去重**：首页「涨停率 ≥□%」与「评分 ≥□ 分」筛的是**同一个字段 `probability`**，
> 已合并为一项「**分数 ≥□ 分**」（绑定 `scoreFloor`，沿用单阈值硬门槛；内置默认 **50**，
> ⚠️ 2026-09-20 起 clamp 下限同时卡到 50 ⇒「0=不限」已取消；线上实际值由管理员后台设定），
> **选股名单零变化**。⚠️ `probLt/confLt` 无 UI 入口但仍按默认 65/65 传后端 →
> 分数调到 **65 以下**时"双低"判据会额外生效（既有耦合，解耦需改后端）。

> **v4.11.21 流通市值筛选合并为区间一格**（2026-09-14）：原「流通 ≥□亿」与「流通 ≤□亿」
> 两个独立格 → 合成一格显示 **`[下限] ≤ 流通 ≤ [上限] 亿`**（`.mv-range-op` 中间运算符）。
> 🔴 符号用 **`≤`（非严格）**：`filters.js` 判据是 `mv < 下限 → 剔除` / `mv > 上限 → 剔除`，
> 等价于 **保留 `下限 ≤ mv ≤ 上限`（含边界）** —— 首版误写成严格 `< 流通 <` 属"文案与行为不符"，
> 已修正；并由 2 例「边界含」单测锁死（两段重复判据各一）。**不要照抄需求里的字面符号。**
> **绑定字段不变**（下限 `floatMvFloor` / 上限 `floatMvGt`）→ `filters.js` 过滤语义、
> 偏好持久化、后端传参**全部零影响**；两端 `0` 仍表示「不限」。筛选行单元数 6 → 5。
| 名单 | **9:30 前锁定后恒定** | 每日最新报告（历史回看走导航「历史回看」页 AI 预测 tab） |
| 落库/推送 | lock 落库 + 推送 | 报告独立存储 |

### 选股闸门 v4：只认当日 9:25 定格，竞价进行中整段不出名单（v4.11.29，2026-09-18）

**当前口径（一句话）**：交易日 **`09:15:00 ~ 09:25:35` 整段不出名单**，**09:25:36 起**放行
（还须再过**快照维**：当日 9_25 已落库）；**盘前 00:00~09:14:59 放行**，但由顶栏**常驻标注**
"当前为 X 日定格数据"明示来源；**非交易日不拦**（回放最近交易日定格，同样标注）。

> 🔴 **和"竞价窗口"的关系（本版最重要的一句）**：v4.11.27 的理由是「竞价数据在变，但那正是
> 用户要看的实时竞价」，故 `09:15-09:25` 放行。**主人 2026-09-18 推翻了该理由**：
> 「**选股本来就是竞价结束后才选，竞价过程数据都在变化，选的股也没意义**」。
> 同时该时段取数会**静默回退上一交易日 9_25**（竞涨幅占评分权重 **34%**）→ 名单与评分双双失真。
> ⇒ 竞价进行中**不再提供名单**。演进：v4.11.22「9:00-9:26 整段禁」（误伤竞价主窗口 + 掐死前端
> 自动加载 → 9/17 早盘事故）→ v4.11.26 回退 → v4.11.27「只挡两段」→ **v4.11.29「只挡一段」**。

**同步落地：定格前的批次不再被复用 / 回显（v4.11.29 的另一半，与闸门开关无关）**

即使闸门开关关着（生产当前即如此），下面这条**硬判据**依然生效 —— 它治的是
「**早上 9:15 落的批次，竞涨幅整批是昨天的，却整天被 refresh 直读 + 前端首屏回显**」:

| 项 | 口径 |
|---|---|
| **判据** | 批次 `ts >= 当日 9_25 快照的落库 ts`（`history._freeze_landing_ts(bdate)`，该时点全部行同一值） |
| **为什么不用固定时刻** | 落库时刻每天漂（**实测 09:25:23~09:25:32**），而**系统批次（#9_25）由落库事件本身触发** —— 9/18 实测 **#1676 只比落库晚 3 秒**（`snapshot ts=1789694726` vs `#1676 ts=1789694729`）。用固定 `09:25:36` 会把这份**合法**名单误判成"定格前" → 掉到跨日回退 → 显示昨日名单。 |
| **落地位置** | `find_today_reusable_batch` ①②（当日同参 lock/filter）+ ③ `_today_system_batch_id` + `find_today_system_batch` |
| **前端怎么判** | `list_batches` 每行透出 **`freeze_ready`**，前端 `stores/stocks.js` 首屏回显消费它（`x.batch_date === today && x.freezeReady === true`）。**前端不得自己猜时刻**（它拿不到 `snapshot_bid` 的落库时刻），有反向防线单测钉死。 |
| **定格前名单会丢吗** | 不会。**不删除**，仍可在「历史回看」里查到；只是不再被当作"当日权威名单"复用。 |

⚠️ **两个口径不要混**：`mode.T_PICK_OPEN`（**现 09:26:31**，随定格时刻顺延三次：09:25:36 →
09:25:51 → 09:26:31）是**用户体验口径**（覆盖最晚落库，该窗口内不让用户发起请求）；
`_freeze_landing_ts` 是**数据真伪口径**。用途不同，不可互相替代 —— 故此处**刻意不写具体值**。

**定格来源对用户可见（v4.11.29）**：`auction_snapshot.freeze_source_date()` →
`stocks._freeze_fields()` → 返回体 `freezeDate` / `freezeIsToday`（lock 幂等直读、refresh 直读批次、
计算缓存命中、最终结果**四处**都带；查库异常返回 `{}`，宁可少标不误标）。
前端 `StockView.vue` 的 `.freeze-notice` 黄色标注条：**与闸门提示互斥、与名单并存**
（盘前/非交易日/回放时出现：「当前为 **2026-09-17** 定格数据（上一交易日 / 回放），改条件可重选」）。

> 🔴 **模板坑**：标注条**必须放在 `v-else` 分支内部**。放在 `v-if` 与 `v-else` **之间**会打断
> v-if/v-else 链，Vue 编译期报 `X_V_ELSE_NO_ADJACENT_IF`，**构建直接失败**；
> 也不能用 `v-else-if` —— 那会把名单顶掉（标注要和名单同时可见）。

### （存档）选股闸门 v3 与 09-17 早盘事故复盘 —— 回退前的历史记录

> 🔴 **以下为 v4.11.22 ~ v4.11.27 的历史存档**，口径已由上面的 v4 取代，**仅作事故复盘用**。
> `v4.11.26` 曾把闸门整体回退并从代码中摘除；`v4.11.27` 以「只挡两段」重做；v4.11.29 收敛为一段。

**规则（v4.11.22 存档）**：交易日 **9:00 ≤ now < 9:26 → 关闭选股**；非交易日（周末/节假日）
与 **00:00-9:00 盘前不拦**（盘前「看上交易日定格」是 PREOPEN 的既有设计）。

**上线状态**：~~生产 + 测试机均已生效~~ → 🔴 **已于 v4.11.26 回退并下线** →
v4.11.27 以「只挡两段」重做并部署测试机 → **v4.11.29 收敛为「只挡一段」并部署测试机**
（回滚点见 history v4.11.22 / v4.11.24 / v4.11.26；**当前口径以本节开头为准**）。

> 🔴 **09-17 早盘事故（v4.11.24 闭环，务必先读这段再看下面的"为什么必须禁"）**：
> 闸门上线后次日早盘，主人报「9:26 到 9:30 刷不出数据、9:30 后像是昨天的」。四层根因：
> ① **闸门把 9:15-9:26 竞价主窗口也关了** —— 而这是**主人的真实选股来源**（9/16 该窗口产出
> 13 批 / 98 只 / 均分 7.5 / 最高 35）；更糟的是**前端置灰是纯时间判断、不看开关** →
> 用户**连按钮都点不动**，后端日志「选股闸门拦截」= **0**（不是闸门失灵，是请求压根没发出）。
> ② `use_snapshot_pool` 分支不对称（**既有缺陷**）：`lock` 只在 **9:15 前**用快照池 →
> 9/16 与 9/17 的 09:26-09:30 都是「~2 只」，行为一致，**证明不是闸门造成的**。
> ③ 17% 因子口径改动把全市场评分压低 5~17 分 → 最高 66 < `scoreFloor=80` → 当日**一个系统批次都没落**。
> ④ 无当日批次 → `find_recent_reusable_batch(lookback_days=14)` 命中 9/16 →
> 日志「回退最近交易日直读 date=2026-09-16」当日 **756 次** → **用户看到的就是昨天的名单**。
>
> **结论**：闸门治好了「9:25-9:26 静默回退昨日」，却把「9:15-9:26 实时竞价选股」一起治死了，
> 且因为前端不看开关而**丧失了最轻回滚能力**。
> ⚠️ 该事故当时的候选口径（只挡 9:00-9:15 + 9:25:00-9:25:35）**已被 v4.11.29 取代** ——
> 主人 9/18 重新拍板：**竞价进行中整段不出名单**（理由见本节开头），盘前段改为放行 + 标注来源。
> **生产 `pick_window_guard` 仍为 0。**

**为什么必须禁** —— 该区间三种情况都只能给出**非当日定格**的名单：

| 子时段 | 原行为 | 问题 |
|---|---|---|
| 9:00-9:15（PREOPEN） | 用**上交易日** 9:25 定格 | 用户误以为是当日名单 → v4.11.29 改为**放行 + 顶栏标注来源日期** |
| 9:15-9:25（AUCTION） | 实时全市场，名单随行情变；且当日 9_25 未落库时**竞价字段整批回退昨日** | 9/16 实测 9:19 出 9 只 → 9:25 只剩 2 只；9/18 实测 #1674 竞涨幅逐位=昨日 → **v4.11.29 整段禁** |
| **9:25-9:26（LOCKED 早段）** | 当日 9_25 **尚未落库** → `load_snapshot_full` **静默回退昨日** | 🔴 9/16 有 **2 个用户**（09:25:14 / 09:25:29）拿到 **9/15 的名单**，日志只有一句 INFO |

> 9_25 定格**落库时刻**由**定格首采时刻** `_BID25_FREEZE_SEC`（v4.11.45 起固定 **09:26:30**）
> 与重采截止 `_BID25_RETRY_UNTIL=09:27:30` 共同决定：定格枪 09:26:30 开枪，全市场拉取 8~15s
> ⇒ 实际落库约 **09:26:38 ~ 09:26:45**，而闸门放行点 09:26:31 之后仍留 **7~14 秒**空窗，
> 所以**快照维不能省**（纯时间闸门会放行而仍回退昨日）。
> 历史（v4.11.43 之前）：采集下限 20s/45s + 重采窗口 09:25:50，实测落库 **09:25:23 ~ 09:25:32**。

**双闸门实现**（两维都过才放行）：

| 维度 | 位置 | 判定 |
|---|---|---|
| 时间维 | `picker/mode.py` → `is_pick_open(now, holidays)` | 交易日 `T_PICK_BLOCK_FROM(09:15:00) ≤ s ≤ T_PICK_BLOCK_TO(09:26:30)` → 关；`≥ T_PICK_OPEN(09:26:31)` 交快照维 |
| 快照维 | `auction_snapshot.py` → `has_today_snapshot(date)` | 当日有无 9_25 行（`SELECT 1 ... LIMIT 1`，走 PK 索引）。**查库异常返回 False（保守拦住）** |

接口层落在 `api/stocks.py`（在 `action=ping` **之后**，故 ping 天然放行）：命中直接返回
`{ok:false, blocked:true, msg, blockedUntil:'09:26:31', list:[], count:0}` —— **不跑 pipeline / 不落批次 / 不推送**。

| 放过 / 拦截 | 说明 |
|---|---|
| ✅ `action=ping` | 在闸门之前 return，前端登录态与时段探测不受影响 |
| ✅ 历史回看 | `/api/stocks` **没有 `date` 参数**，历史回看走 `batches` 接口 → 天然不受影响 |
| ✅ `system_batch`(uid=0) / `auto_apply` | 走 `picker/lock.py`，**不经过这道 API 闸门**（且 lock 本身拒绝 PREOPEN/AUCTION） |
| ✅ 竞价异动页 | 独立模块，9:20-9:25 正是它的主场 |
| ✅ `/api/picker/snapshot` | `read_snapshot_rows` 直接 `WHERE date=?`，**不跨日回退** |

**前端表现（置灰 + 文案）**：`utils/time.js` 的 `isPickBlockedTime(bj)`（与后端**同口径**，
常量与文案由后端单测 `test_pick_block_msg_shared_with_frontend` 对拍）+ **纯函数
`isPickGateOn(enabled, bj)`**（v4.11.24 新增，零依赖便于 `node --test` 直测）；

否则用户在 9:10 打开页面会一直停在禁用态。若后端因「定格尚未落库」继续拦，下一轮自动重试。

🔴 **置灰必须由后端开关驱动（v4.11.24）**：原先前端只看时间、不看 `pick_window_guard`，
于是「关开关」只关后端 —— **前端依旧置灰且连自动加载都不发请求**，等于**最轻回滚开关失效**。
现在改为：
- `api/stocks.py` 的 `action=ping`（在鉴权后、**闸门之前** return）额外返回 `pickGateEnabled`；
- 前端 `api/stocks.js::pingStocks()` 探测，`stores/stocks.js` 的 `_loadPickGateEnabled()`

- 三个入口 `fetchAndCache` / `reLockData` / `applyCustomFilter` 由 `if (isPickBlockedTime())`
  改为 `if (this._pickGateOn())`；`StockView.vue` 首屏 `refreshPickGate(true)` **强制探测**一次；
- 解禁时若本地无缓存会**自动补拉一次**，不用用户手动点。

⚠️ **`bool()` 真值陷阱**：开关解析**必须用 `stocks._pick_window_guard_on()`**（单一口径处），
不能写 `bool(settings.get(k, 1))` —— 后者对字符串 `"0"` 判成 **True**（非空串 truthy）→
**「关开关」会静默失败**。该 helper 显式解析 `0/"0"/"false"/"no"/"off"/""`，并有单测钉死。

**开关**：`settings.pick_window_guard` 默认 **1**（库中无键即开）；后台置 `0` **即时回滚，无需重启**
（**v4.11.24 起前端会跟随该开关实时解禁**，不再需要用户等前端时间到点）。

**全市场预计算物化表（v4.11.11，2026-09-12）**：评分 5 因子（竞价涨幅 34% / 换手率 32% /
异动等级 17% / 流通市值 11% / 昨日涨幅 6%）的输入**全部在 9:25 定格**，唯一活字段是实时涨幅
—— 因此全市场评分可以**在开盘前一次算好**。`picker/precompute.py` 在 `system_batch` 9:26 批跑
**之前**执行，把 5557 只的评分与定格字段写入物化表 `stock_score_daily`
（PK `(date, code)`，`INSERT OR REPLACE`）：实测 **1.5s / 覆盖 99.9% / 幂等**。

三条铁律（缺一不可）：① **不由网络可用性漂移**（唯一例外是 `prev_close` 这类静态值）；
② **缺失写 NULL 不写 0**（0 是"实测为零"，NULL 是"未知"）；③ **行数 < 500 不落半张表**。
读写开关分离：`precompute_read`（读侧走物化表）/ `precompute_write`（写侧产出物化表）
**默认全关**，关时行为与改动前完全一致；物化路径**不豁免 `scoreFloor`**
（补丁源全不可用时才豁免，仅原路径）。补丁源合并后由 `_refreeze_locked` 还原定格字段。

用户改筛选条件只是对**同一份结果**换门槛 —— 不必再跑取数/评分。故后端一次性下发
全市场快照，前端在浏览器内完成筛选：

四条边界（缺一不可）：① 开关 `frontend_local_filter` **默认 0**，关闭时只回

② 门禁与竞价异动同级；③ **行数闸门** < 500 行视为不可用，**绝不发半张表**；
④ 过滤规则**逐条复刻**后端 `coarse_filter + apply_filters`（含"竞额降序取前 120"截断
位置与"评分降序 + code 字典序"排序），两侧共用夹具 `tests/fixtures/picker_parity.json`
各跑一份对拍测试。

> **口径坑（改代码必看）**：`bidGt` 是竞价涨幅上限且**无 `>0` 判断**（填 0 = 上限 0% ≈ 全剔），
> 而 `floatMvGt`/`priceGt` **有 `>0` 判断**（填 0 = 不限）—— 同后缀不同语义，必须逐字段照抄。

**未知 ≠ 0（v4.11.13）**：落库 `_safe_num` 把 `None` 兜成 0 是为了绕过 `NOT NULL` 约束
（并保证排序稳定），但 **0 是有业务含义的实测值**，两者混淆会让前端把"没数据"显示成
"实测 0.00%"（9/11 全员现涨 0.00% 事故的表征之一）。闭环做法：落库用 `_num_or_mark`
把**被兜底的键**记入 `batch_stocks.miss_fields`；读侧开关 `history_null_restore=1` 时
把这些键还原为 `null`。前端全链路容错：**未知显示「—」，实测 0 仍显示 0**
（`utils/format.js` 的 `fmtNum`/`pct`/`signed` 统一口径）。两个开关**默认 0**。

**竞价锁定名单语义**：9:30 前 lock 的名单恒定不变（后端 lock 批次为权威 + 本地快照兜底）。9:30 后刷新时名单不增删，只按 code 合并全市场实时行情（spotMap）更新实时涨幅/评分；被筛选条件剔除的票直接移除，条件放行但行情不在榜的标"已跌出"。

**评分门槛 scoreFloor**（v4.10，9/10 主人拍板，全站默认 **80**、条件面板/管理后台可配）：评分低于门槛的票**直接不入选**。与既有 `probLt`/`confLt` 的区别务必分清——

| 机制 | 语义 | 结果 |
|---|---|---|
| `probLt` + `confLt`（双低剔除） | 概率 < probLt **且** 信心 < confLt 才剔除 | 高信心可以救低概率票 |
| `scoreFloor`（单阈值硬门槛） | 不看信心，评分 < 门槛一律砍 | 低分票不给展示机会 |

实现要点：门槛只能放**精筛**（评分之后）——粗筛在评分前跑，拿不到 `probability`；统计键 `score_floor`。默认 80 下 Felix518 原条件 14 只 → 6 只（评分 81~88）。

**降级豁免**（v4.11.7，9/11 修）：补丁源（**v4.11.47 起为猫爪点查 → 东财点查 → 腾讯点查，三级**）**全部失败**时，候选行只剩 9:25 定格字段——换手/量比/异动/昨日涨幅全缺，算出来的 `probability` 是**保守占位分**（只有竞价涨幅 + 流通市值两个因子可得），不是"这只票差"。若不豁免，`scoreFloor` 会把「点查失败 → 快照行直出保名单」这条降级保命路径整批砍成**空名单**（该路径的设计目标恰恰是"行情源全挂时名单也不为空"）。实现：`FilterContext.score_floor_exempt`，由 `pipeline.run` 在补丁源不可用时置位。**豁免只作用于评分门槛**，板块/ST/竞涨/市值/竞额等硬条件照常生效（有专门用例锁这一点，防"降级=不过滤"）。

**lock 当日幂等**（v4.6，9/2 主人确认语义）：**9:25 后** + 同筛选参数（指纹 = 筛选参数 + markets 集合）的自动 lock（页面加载/重新登录触发）**直读当日批次**返回——不再全量重拉行情/重复落库/重复推送（解决"每次重新登录都重算一次+堆 lock 历史"）；API 返回 `idempotent:true`，前端 toast「✅ 已载入今日锁定名单」。**9:25 前不幂等**（竞价数据未定型，每次进页重算拿最新）；**用户主动点「锁定」带 force=1 强制重算**落新批次；筛选参数改过也不幂等（正常重算）。另 filter 60s 同参去重（`recent_same_filter`），防脚本/手滑反复点应用刷历史批次。

**休市回退秒开**（v4.8，9/5 多用户反馈"关闭平台后再打开首页转圈"）：**9:30 后 / 休市时间**首屏 refresh 在当日无批次（非交易日、当日系统批次为空、当日无手动批次）时，后端 `history.find_recent_reusable_batch` 自动回退 **14 天窗口内最近交易日**的同参批次直读——**关闭前选出的名单直接呈现**（`reusedDate` 标识数据日期，前端 toast「已载入 X 的选股名单」）；参数指纹不一致（用户改过条件）仍走重算；窗口内无任何手动批次才回退最近系统统一批次（空名单批次无直读价值跳过）。生产实测 96ms vs 重算 2.6s+（27 倍）。

**左视图抢筹口径**（v4.5）：**命中右视图竞价抢筹三表并集才打抢筹标**（`get_qiangchou_codes` 合并 list20 竞额强度/list20Chg 9:20→9:25 涨幅/listLast 最后一秒段，30s 缓存，与竞价异动页口径一致）；集合为空/未传回退旧公式（涨幅≥2% 且 竞/昨≥20%）兜底。打标结论**落库 batch_stocks.qiangchou 列**（老库自动 ALTER），9:30 后锁定名单历史回看可显示 🔥。

### 竞价抢筹双表（核心）

- **左表（9:20-9:25 段）**：开盘啦 Type4 全市场竞价异动 200 只，`抢筹强度 = 竞价净额 / 流通市值 × 100`，过滤 `>5%` 且 `流通市值 ≥ 2亿`；竞价时段实时拉取 + 持久化 `qc_snapshot` 表。**涨幅抢筹**（第二表）过滤链：流通市值≥2亿 + 竞价额>0 + 竞价额≥500万 + 竞价涨幅>2%
- **右表（最后一秒）**：`snapshot_lastsec` 秒级高频采样（9:24:55-9:25:03 每秒一次，ts 记实际时刻），**差值回退算法**：
  1. `9_25 涨幅 − 最新秒涨幅`，|差| ≥ 0.5% → 直接用（最后一秒抢筹）
  2. 差太小（接口延迟导致最新秒已含变化）→ 向前回退：最新秒 − 倒数第二秒，依此类推取第一个大差值
  3. 全部差值小 → 取最大差（弱信号）；无秒级序列 → 回退 9_24 时点兜底
- **竞额/昨比列**：双表「竞价换手」列改为「竞额/昨比」= 今日竞价额 ÷ 昨日全天成交额（`fetcher.fetch_yesterday_amounts` pair[0]），≥20% 橙色高亮 / ≥10% 黄色
- **非竞价时段**：读库展示今天已选结果（不丢失）；**实时模式自动回退**：今日无快照时自动回退最近交易日（盘前/周末可看昨日数据，`date` 字段透出实际日期）

## 概念开盘啦化（全部股票）

选股列表 / 历史回看 / 竞价异动的**所有股票概念**统一替换为开盘啦风格（短板块名顿号分隔，如 `机器人概念、股权转让、汽车零部件`），替代东财 f103 逗号长串。实现为**双层覆盖**（`kpl.apply_board_concept`）：

1. **榜单层（快）**：开盘啦 5 路榜单接口合并（连板梯队/涨停委买/爆量/热点股/9:25 快照）→ 一次拿到 86+ 只热点股板块
2. **按股层（全）**：对榜单未覆盖的股票逐个调 doc94 `GetStockIDPlate`（个股全部相关概念板块）→ **100% 覆盖**；`ThreadPoolExecutor` 分批并发 + 每只 1 天缓存

**覆盖范围**：竞价选股（落库前覆盖 → 页面/历史批次/推送统一）、盘中选股、历史批次明细、历史聚合查询。**前端只显示前 2 个概念**（`shortConcept`），完整列表 hover title 查看。

**概念定时落库（v4.1）**：`stock_concept` 表 + `concept_refresh` 每半小时从所有竞价/上榜实时接口采集批量写库（覆盖盘中新增，如竞价爆量 407 只）；竞价各接口改从库读（`apply_board_concept_db`），不再每次请求实时逐股查 → 全表格概念 100% 覆盖且低延迟。

**防限流设计**（踩坑修复）：`_call` 加全局信号量（并发 3），失败结果不缓存（避免 1 天空串缓存），按股查询分批 20 只/批。

### 异动等级（17% 因子）数据源：东财 f630 随定格落库（v4.11.30，2026-09-18）

**17% 权重的「异动」因子取东财 f630 异动等级**（`use_bid_strength=0`）；
`=1` 时用「竞价强度」（三层：快照自算量比 + 开盘啦抢筹 + 9_24→9_25 加速度，对东财免疫）。

**为什么 f630 要「采集时落库」而不是只靠运行时点查** —— 定格链路（9:25 后选股）的**名单行来自
`snapshot_bid`**，`QuoteRow.from_snapshot` 不设 `warn_type` ⇒ 不落库就只剩「补丁源」一条路，
而补丁源曾**长期不可用**。两条路的实测：

| 通路 | 实测 | 后果 |
|---|---|---|
| **点查** `push2dycalc…/api/qt/ulist.np/get`（选股补丁源 `eastmoney_realtime`） | ✅ 通（**v4.11.33 修复后**）—— 同一 path 下**域名决定生死**：`push2.` ❌ `RemoteDisconnected`(48ms 秒断) / `push2dycalc.` ✅ `rc=0` **且带 f630** | 补丁源恢复可用。修复前**必然失败** → 每轮退腾讯点查（**腾讯无 f630**） |
| **全市场 clist** `push2dycalc`（`config.FIELDS` 本就含 f630） | ✅ 通，实测全市场 **5917 只里 2280 只非 0（38.5%）**，取值域 0~14，无一只返回 `-` | 采集那一秒顺手落库 → 定格链路拿到权威值 |

⇒ 两条路现在都通，但**落库仍是权威**：它把 **9:25 定格那一秒**的 f630 固定下来，
**不依赖运行时任何外网调用**（补丁源可能因熔断 / 域名 / 风控随时不可用）；
点查则保证「运行时补值」这条路也活着（v4.11.33 起其返回的 diff 实测带 f630）。

⇒ 采集时把 `f630 → snapshot_bid.warn_type`（`INTEGER NOT NULL DEFAULT 0`，老库幂等 ALTER 迁移），
`load_snapshot_full` 透出、`QuoteRow.from_snapshot` 读入，定格链路才有权威异动等级。
**不这么做的话，翻开关 = 17% 权重退化为常数**：全市场 warn_type 落 `default 0.18`，
概率天花板从 99.4 掉到 85.5（9/8 批次#1585 全 39 只 warn=0、9/17 一整天零名单两次事故的同一根因）。

|---|---|---|---|---|
| 因子分 | 0.60 | 0.85 | 1.00 | default **0.18** |

**实测分布**（2026-09-19 全量分页；**口径务必看清**）：全市场 5917 只 ——

⚠️ 早前记录的「5856 只里 1268 只非 0（21.7%）」是**把沪深主板的非 0 数错配到全市场总数上**，

**两条降级纪律**：

- **老库缺 `warn_type` 列时降级而不是让名单失踪**：`_select_snap_rows` 捕获 `OperationalError`

  1. **板块天然覆盖率差异**（2026-09-19 实测，与分页成败无关）：

  2. ~~**间歇性分页失败**~~ → 🔴 **2026-09-19 查清并修复**：并非"偶发失败"，而是

### 流通市值口径（v4.11.28，2026-09-18）

**一个字段两种语义，曾经让 49 亿的票被 30 亿门槛剔掉。** 全系统 `float_mv` 列的语义固定为
东财 f21 **流通市值**；开盘啦的 `floatMv` 是**实际流通（≈自由流通）**，量级只有前者的 0.28~0.73。

- **采集侧**：东财全分区失败转开盘啦兜底时，开盘啦值写 `free_mv`、`float_mv` 留 0，
  由 `mv_cache.fill` 用东财 f21 / 腾讯 f44 补真流通市值（补不到就保持"未知"）。
- **缓存侧**：`stock_float_mv_daily` 只回写**确实拿到流通市值**的行（`INSERT OR REPLACE`
  不会再用 NULL 冲掉真值）；`src` 精确标注 `tencent` / `em` / `cache:<来源日期>`，来源可追溯。
- **门槛侧**：**市值未知不剔除** —— `coarse_filter` 与 `_snapshot_candidate_codes` 都放行给
  `apply_filters`（彼时点查补丁已补到真值），判定不再随行情源可用性漂移；门槛判据统一用
  `float_mv`，`free_mv` 只做缺失兜底。
- **效果**：9/17 实测 56 只"真流通 ≥30 亿却落库成 <30 亿"的误剔全部消失；历史数据已回溯修复
  （9/11~9/17 三张表，脚本 `scripts/deploy_tmp/_fix_mv_caliber_0918.py`）。

### 落库任务时刻与自愈（v4.11.16，2026-09-13）

历史落库曾**自上线起长期空转**（`limit_history` 停更 12 个交易日、`lhb_history` 停更 20 个），
根因不是"调度没跑"，而是**采集时刻早于上游发布**，且失败后既不重试也无次日补救：

- **时刻修正**：涨停/炸板（上游**选股宝 flash 池**，当日数据 15:50 后才发布）与龙虎榜
  （盘后公布）统一由 **15:30 → 18:30 晚间窗**（18:10~18:50），龙虎榜单独占 18:30~18:40。
- **失败退避重试**：`_fired` 改为**成功后才置位**，窗口内失败按 300s 起、翻倍、上限 1800s 重试，
  并加 `_running` 防重入 —— 旧逻辑"起线程即置位"= 窗口内只试一次，上游一迟就当天废弃。
- **失败回滚**：龙虎榜 `setnx` 占锁后判空**补 `store.delete`**（旧逻辑不释放 → 一次空即当天全废）。
- **次日盘前自愈**：新增 **09:00~09:05 补救窗**（避开 9:15 竞价主流程），回溯最近 7 个自然日，
  按 `INSERT OR REPLACE` 幂等补齐 `limit_history` / `lhb_history` 缺失交易日
  → 晚间窗因重启/节假日错过时，次日开盘前自动兜住，缺口不再累积成长缺口。

### 日K 缓存新鲜度与股性画像（v4.11.16 修 + 09-13 生产重建）

- **原缺陷**：`_kline()` **命中缓存即永久返回、无过期判断**，而 `rebuild_profiles()` 默认
  `refresh_kline=False` → 日K底座永久冻结在首次写入时刻（生产实证 `stock_kline` 与
  `stock_temper_profile` 的 `ts` **全部 = 8/27**，相差 11 个交易日）。**只调时间窗治不好**，
  必须修 TTL。
- **修复**：末根日期 < 期望最近交易日（收盘 15:05 前取上一工作日）→ **回源**；
  解析不出末根日期时按"新鲜"处理（避免异常形态下全量回源打爆上游）。
- **生产重建（09-13）**：一步 `rebuild_profiles()` 完成治本 —— **3978 只 / 861.6s / 失败 0**，
  日K **回源 3951/3978**（TTL 生效后命中率 99.3% → 全量回源），`ts` 全部刷新。
  → 样本 002790 瑞尔特：`zt_count`（近一年累计**封板次数**）**4 → 8**、`max_zt`（最大**连板高度**）仍 **4**。
  ⚠️ 两个字段语义不同，汇报"几板"必须写清是次数还是高度。
- **运维提示**：跨机外推耗时**乘 2 倍安全系数**（测试机 0.105s/只 → 生产 0.217s/只）；
  生产 DB 是 WAL，在线大批量写不阻塞读，此类重建可在线跑。

## 系统自动选股批次（历史回看保障）

- **问题**：历史回看数据来自 batches 表，用户当天没点选股 → 无记录 → 无法复盘
- **方案**：9:25 快照落库后 worker 自动跑 system_batch（`user_id=0 + auto_applied=1`），历史回看对所有用户合并展示
- **过滤与首页左视图一致**（8/31 修复）：复用管理员全局默认筛选（1000 亿市值上限 / 300 元股价上限 / 剔除 ST / 竞价金额 ≥1000 万），管理员后台改默认自动同步——不再出现"自动批次锁的是小票池≈AI 预测数据"的错位
- 🔴 **口径真正对齐**（v4.11.46，09-24 修）：上面那次"复用"**只做到一半** —— `system_batch` 当时
  **又自带一份 9 键副本**（缺 `scoreFloor`），且合并用 `if k in merged` 白名单 ⇒ settings 里的
  `scoreFloor` 被**静默丢弃**，实际吃的是 `picker/lock` 的硬编码兜底 **50**（线上首页是 **60**）。
  实测同一时刻同一份快照：**系统批次 64 只 vs 首页左视图 27 只**。
  现四份默认值已归口到 `backend/app/services/filter_defaults.py`（**唯一真相源**），
  `admin` / `system_batch` / `auto_apply` / `picker/lock` 全部引用**同一对象**
  ⇒ 系统批次从此**含 `scoreFloor`** 且**随管理员后台调整**（此前固定 50、不受任何后台配置影响）。
  ⚠️ **存量不回算**：已落库历史批次的 `filters` JSON 里仍无该键（回看页读库、不重算名单），
  仅**未来**批次生效。
- **抢筹打标落库**（v4.5）：batch_stocks 表新增 `qiangchou` 列（老库启动自动 ALTER），系统自动批次与用户手动批次都写入抢筹标结论 → 9:30 后锁定名单/历史回看可显示 🔥
- **监控**：9:26:30 自动检查当日 system_batch 是否落库，缺失 → 补跑 + 飞书/微信告警（setnx 跨进程去重防重复告警）
- 9:15/9:20 时点暂未生成（聚焦 9:25 竞价结束时点，如需可扩展）
- 🔴 **刷新直读的选批优先级（v4.11.25 修正，9/17 事故闭环）**：`action=refresh`（9:30 后）
  按序直读，命中即返回（不重算、不转圈）：
  1. 用户当日手动 `lock` **同参**（`auto_applied=0`，`stock_count>0`）
  2. 无 → 用户当日手动 `filter` **同参**
  3. 无 → **仅当用户当日无任何手动批次** 时，用当日系统统一批次（`user_id=0, auto_applied=1`）
  4. 无 → **当日系统统一批次**（`history.find_today_system_batch()`，**无视是否有手动批次**）← v4.11.25 新增
  5. 无 → 跨日回退（`find_recent_reusable_batch`，14 天窗口内**最近日期同参**批次）

  **为什么必须有第 4 步**：9/17 事故中，用户当日**点过** lock/filter 但落的是**空名单批次**
  （当日评分被压到 `scoreFloor` 之下 → `候选=7 入选=0`）→ 第 1/2 步因 `stock_count=0` 跳过、
  第 3 步被 `if not rows` 挡住 → 直落第 5 步 → **交易日却显示 9/14 / 9/16 的名单**（实测 756 次）。
  第 4 步的语义是"**当日系统名单对用户一定优于任何昨日名单**"。
  ⚠️ **不能简单去掉第 3 步的 `not rows`** —— 那会让"改过筛选条件"的用户错误直读系统名单
  （违背"改条件必须重算"），故采用**另加一步**。命中第 4 步时 `reusedDate` 为 `null`，
  前端**不会**提示"这是历史名单"（因为它就是当日名单）。
  ⚠️ 相关测试：`backend/tests/test_today_system_fallback.py`（含事故正向回归 + 反向对照），
  日期**按今天相对推算**（写字面量日期的用例会随日历漂红）。

## `auto_apply` 幂等锁：一日一次 → **成功才置 done + 60s 节流**（v4.11.27，2026-09-17）

**缺陷（旧实现）**：`store.setnx("sched:auto_apply:" + date, 1, ttl=86400)` —— 一把**每日一次性锁，
且在成功前就被消费**。无票可锁时 `_pick_result()` 提前 `return error`，但锁已经烧掉 →
09:26-09:30 剩余的 ~24 轮全部被挡 → **当日永不重试**（若 9:25 定格恰好晚落库，当日就彻底没有系统名单）。

**新实现**：拆成两个键 ——
- `sched:auto_apply:done:<date>`：**只有成功才置**（ttl 86400）；
- `sched:auto_apply:try:<date>`：60s 节流（`AUTO_APPLY_RETRY_SEC = 60`）。

`should_trigger(bdate) = (not already_done(bdate)) and try_acquire(bdate)`；
`auction_snapshot.py` 的 9:26 触发点改为调用 `auto_apply.should_trigger(date)`。
09:26-09:30 共 5 分钟 → 最多约 5 次尝试；**成功即不再重试**，失败则下一分钟再来。
两个 `error` 分支**刻意不置 done**（这正是修复要点）。

回归防线：`tests/test_auto_apply_retry.py`（7 例，含「失败不置 done + 节流过后可重试」核心时序）。
