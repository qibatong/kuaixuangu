# 后台「用户登录记录 + 功能使用记录」— 需求与实施方案（待主人批准）

> 状态：**方案（未开发）**。批准后实施，落库版本号 **v4.11.35**（按 `AGENTS.md §0.4` 版本迭代规则）。
> 调研时间：2026-09-22（全部数字为**生产机实测**，非估算的部分已标注；估算部分标「估算」）。

---

## 0. 结论先行

**可以做，而且存量数据大部分已经存在**——现网 journald 里已经按 `uid` 记录了 08-17 至今的请求流水
（09-21 单个交易日：67,689 行日志，其中**带 uid 的鉴权请求 18,798 条、涉及 24 个用户、67 个 API 路径**）。

所以本次要做的不是「从零开始采集」，而是三件事：

1. **结构化落库**（现在这些记录只存在于文本日志里，随时会被轮转丢掉，后台查不了）；
2. **后台可视化**（用户详情抽屉 + 运营看板卡片）；
3. **存量回溯**（把 journald 里已有的历史一次性灌进新表 —— 但这是**有窗口期的**，见 §2.5）。

---

## 1. 现状实测：现在到底有什么、缺什么

### 1.1 登录记录 —— 几乎没有

| 来源 | 有什么 | 缺陷 |
|---|---|---|
| `tokens` 表（79 行） | 每行有 `created_at`（= 登录时刻）、`revoked` | **无 IP、无 UA、无失败记录**；token 过期被访问时会被 `DELETE`（`security.py:75`）⇒ **历史会丢**；且单点登录会把旧行 `revoked=1` 而非保留完整链条 |
| `app.log` 文本日志 | 有「登录成功 / 登录失败」行（含 IP） | 实测**全文件只有 11 条**「登录成功」—— 该文件 10MB 即轮转，长期保存不可靠 |
| `admin_audit`（4 行） | 管理员改到期/等级/删号 | **只记管理员动作，不记用户登录** |
| `users.register_ip / register_ua` | 注册那一次的 IP/UA | 只记注册，之后登录完全不更新 |

**实测**：09-21 全天 `journalctl -u kuaixuan` 里「登录成功」18 条、「登录失败」0 条。
另：**前端没有退出登录接口**（`NavBar.vue` 只清本地 token，不调后端）⇒ 目前**没有任何「退出」记录**。

### 1.2 功能使用记录 —— 只覆盖免费用户，且会过期

- 唯一的用量记录 = `kv_cache` 里的计数键 `quota:{feature}:{uid}:{北京日期}`（`quota_guard` 放行时自增）。
- 🔴 三个硬伤：
  1. **会员与管理员不计数**（`quota.py` 明确放行不计数）⇒ **付了钱的人用得最多，却完全没记录**；
  2. **TTL 25 小时**（`86400+3600`）⇒ 过期即删，**无法回溯历史**；
  3. 只有 `picker / aipick / auction` 三个功能，**题材异动、历史回看、连板天梯、市场量能、会员中心全无记录**。

### 1.3 已经存在、可直接回溯的素材

| 素材 | 内容 | 保留窗口 | 是否能定位到用户 |
|---|---|---|---|
| **journald（uvicorn access）** | 每行形如 `时间 IP METHOD /path uid=NNN 状态码 耗时` | **08-17 起，共 316 万行**；⚠️ **已占 3.9G，默认上限 4G ⇒ 已接近开始丢弃最老日志** | ✅ **含 uid**（唯一能回溯用户的来源） |
| nginx `access.log` | IP、UA、referer、状态码、耗时 | 按天轮转保留 `.gz`（09-12 起） | ❌ **不含 token / uid**（实测请求行里没有 query 的 token），只能补 UA |
| `users` 表 | 注册 IP/UA、邀请链、到期、等级 | 长期 | ✅ 但仅注册时 |

## 2. 需要新增的功能（详细清单）

### 2.1 两张新表（`db/database.py`，走 `init_db()` 幂等迁移，不动任何现有表）

**① `login_log` —— 登录明细表**

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK AUTOINCREMENT | |
| `uid` | INTEGER | 成功时为用户 ID；失败时为 0 |
| `login_try` | TEXT | 用户输入的账号（失败时用于排查撞库） |
| `result` | TEXT | `success` / `fail` / `reset`（手机号重置） / `kicked`（被顶出） |
| `ip` | TEXT | `deps.client_ip()`（🔴 反代后必须用它，不用 `request.client.host`） |
| `ua` | TEXT | User-Agent，截断 200 字符 |
| `remember` | INTEGER | 是否勾了「记住我」（30 天 token） |
| `created_at` | INTEGER | 秒级时间戳 |

- 量级：实测 09-21 登录成功 18 次 ⇒ **估算 20~100 行/天**，一年 ≤ 3.6 万行，**可长期保留**。

**② `usage_daily` —— 功能使用聚合表（主表）**

| 列 | 类型 | 说明 |
|---|---|---|
| `uid` | INTEGER | |
| `date` | TEXT | `YYYY-MM-DD`（**北京日期**，与配额口径一致） |
| `feature` | TEXT | 见 §2.2 的 8 个功能键 |
| `count` | INTEGER | 放行次数 |
| `blocked_count` | INTEGER | **被拦截次数**（额度不足/门禁）——转化线索 |
| `first_ts` / `last_ts` | INTEGER | 当日首次 / 最后一次使用时刻 |
| PRIMARY KEY | `(uid, date, feature)` | UPSERT 自增 |

- 🔴 **为什么必须聚合、不能存明细**：全站单个交易日鉴权请求 **18,798 条**（实测）。逐条落库 ≈
  **570 万行/年**，SQLite 单库（现 512MB）扛不住，且其中 90% 是 30s 轮询噪音。
- 聚合后量级：用户数 × 功能数 ≈ 274 × 8 = **2,192 行/天**，一个月 ≈ 6.5 万行，**估算年增 ≈ 60~80MB**。

**③（可选）`usage_recent` —— 最近明细表**：只保留每个用户最近 7 天的功能进入明细（时间 + 功能），
用于在详情页展示「最近在干什么」的时序。**若你不想再加一张表，可砍掉**（用 `usage_daily` 的
`last_ts` 也能表达个大概）。

### 2.2 8 个功能键（与前端入口对齐）

| 键 | 中文名 | 覆盖的入口 |
|---|---|---|
| `picker` | 选股 | 首页今日名单/评分 |
| `aipick` | AI 选股 | AI 选股页 |
| `auction` | 竞价异动 | 竞价异动 8 Tab |
| `concept` | 题材异动 | 猫爪精选板块页 |
| `history` | 历史回看 | 多时点/历史批次 |
| `ladder` | 连板天梯 | 涨停天梯/龙虎榜 |
| `stats` | 市场量能 | 首页量能/情绪面板 |
| `member` | 会员中心 | 我的会员页/签到 |

### 2.3 埋点位置（5 处，全部不改业务逻辑）

1. `api/auth.py::_login_sync` → **登录成功 / 失败**各写一条（该函数已有 `client_ip`，UA 从 `request.headers` 取）。
2. `api/auth.py::api_reset_by_phone` → 记 `reset`（手机号重置密码成功；安全审计价值最高的一条）。
3. `api/deps.py::get_uid` 的 `kicked` 分支 → 记 `kicked`（**账号共享/多设备使用排查**）。
4. **新增 `api/deps.py::track_usage(feature)` 依赖工厂**（与现有 `quota_guard` 完全同风格）：
   - 套在 §2.2 各功能**入口路由**上（每个功能接 1~2 个端点，不是所有子接口）；
   - **对所有用户生效**（会员/管理员也记，另记 `is_admin` 便于剔除内部流量）；
   - 放行 ⇒ `count+1`；被拦截（429/403）⇒ `blocked_count+1`；
   - 🔴 **整段 try/except 兜住**：写失败只打日志，**绝不允许影响业务响应**。
5. **（可选项，需你决定）新增 `POST /api/logout`** —— 现在退出登录是纯前端行为，后端无感知。
   加了这个接口才能记录「主动退出」。不加则只有「被顶出」和「token 过期」两种会话结束痕迹。

### 2.4 新增 4 个后台端点（`api/admin.py`，全部 `get_admin` 鉴权）

| 端点 | 作用 |
|---|---|
| `GET /api/admin/user-activity?target_uid=&days=30` | **某用户**：登录记录（近 N 条）+ 使用记录（今日 + 近 30 天） |
| `GET /api/admin/login-log?days=&result=&kw=&limit=` | **全局登录流水**（结果筛选 + 关键字 + 分页） |
| `GET /api/admin/usage-rank?date=&feature=` | 某日使用排行（口径复用 v4.11.34 的 `usage_top` 思路） |
| `GET /api/admin/active-users?days=30` | 活跃趋势：按日去重用户数 + 功能分布（给看板卡片） |

🔴 **查询留痕**：管理员查看某个用户的记录时，往 `admin_audit` 写一条
（`action='view_user_activity'`，`target_uid=被查用户`）—— IP/UA 属个人信息，谁查了谁要留痕。

### 2.5 存量回溯（一次性脚本，**有窗口期**）

- 做法：`journalctl -u kuaixuan --since <日> --until <日>` **逐日导出**（316 万行不能一次拉），
  用正则解析出 `uid` / `METHOD /path` / 状态码 / 时间 → 映射到 §2.2 的功能键 → 聚合进 `usage_daily`；
  同时抽取「登录成功/失败」行 → `login_log`（**有 IP、无 UA**，UA 可从 nginx 日志按 IP+时间近似补，**不建议**）。
- 🔴 **必须尽快做**：journald 已占 **3.9G / 默认上限 4G**，一旦超限就开始**丢最老的日志**，
  回溯窗口会一天天缩短。
- 建议回溯范围：**近 30 天**（更早的数据对运营决策价值低）。
- 回溯数据只填 `usage_daily`（不含 `blocked_count`——历史上没有这个信息，只能记 0）。

### 2.6 保留期与清理

| 表 | 保留 | 清理方式 |
|---|---|---|
| `login_log` | 180 天 | 挂 `kx-worker` 现有调度，每天 03:30 删过期行 |
| `usage_daily` | 24 个月 | 同上（行数可控） |
| `usage_recent`（若做） | 7 天 | 同上 |

### 2.7 后台界面（**在现有 7 Tab 内扩展，不新增 Tab**）

- **用户详情抽屉**（`AdminView.vue::openUserDetail` ↔ `GET /api/admin/user-detail`）新增两块：
  ① **登录记录**表：时间 / 结果（中文：成功·失败·重置·被顶出）/ IP / 客户端；
  ② **功能使用**：今日各功能次数，+ 近 30 天矩阵（行=日期、列=功能、格=次数）。
- **运营看板 Tab** 新增 2 张卡：今日登录人数与次数；今日活跃用户数 + 功能 Top5。

## 4. 风险与对策

| 风险 | 量级（实测/估算） | 对策 |
|---|---|---|
| 写放大拖慢主流程 | 聚合 **2,192 行/天**（≈ 现有 `stocks` 表日增的 0.4%） | UPSERT + `(uid,date)` 索引；写入异步/兜异常；上线前实测单写耗时 |
| SQLite 单库膨胀 | 估算 **60~80MB/年**（现库 512MB） | 已用聚合；`usage_recent` 只留 7 天 |
| 磁盘（现 `/` 已用 88%，剩 4.6G） | journald 已占 3.9G | 见 §5 第 3 项：把 journald 上限从默认 4G 收到 500M（**需你同意**） |
| 埋点失败影响业务 | — | 全部写入 `try/except` 吞掉 + 日志计数；不影响响应 |
| 隐私（IP/UA） | — | 仅管理员可见；**查询写 `admin_audit` 留痕**；不做（或留痕后）导出 |
| 会员/管理员流量污染统计 | 24 个 uid 里含管理层 | `usage_daily` 增 `is_admin` 维度，排行默认剔除 |
| 轮询噪音 | 实测 09-21 Top 路径 `/api/stocks` 8,174 次、`/api/kpl/index-brief` 7,750 次（多为 30s 轮询） | 见 §5 第 1 项：只记「入口动作」，不记轮询 |

## 5. 需要你拍板的 3 件事（含我的建议）

1. **计数口径：什么算「使用一次」？**
   - **(A) 只算「进入功能」的入口接口**（推荐）→ 数字干净，反映真实使用意图；
   - (B) 该功能下所有接口请求都算 → 数字大，但 30s 轮询会让「8,174 次」这种数字毫无意义。
2. **存量回溯：回溯近 30 天，还是从上线当天开始新记？**
   - 建议**回溯 30 天**（journald 随时会开始丢老日志，现在不做以后做不了）。
3. **journald 限容：是否把默认 4G 收到 500M？**
   - 建议**收**：可回收约 3.4G，直接缓解磁盘 88%；代价是可回溯窗口从 ~35 天缩到 ~5 天——
     所以**要在「先回溯、后限容」的顺序下做**，不能反过来。
