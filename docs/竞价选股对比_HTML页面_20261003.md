## 二、为什么不同（三条硬原因）

### 1) 候选池不同 —— 这是最大的差异

页面 URL：`.../clist/get?...&fid=f3&po=1&pn=1&**pz=200**` ⇒ **只取"当日涨幅榜前 200"**，不是全市场。

| | 他 | 我们 |
|---|---|---|
| 候选池 | **涨幅榜前 200** ✗ | **全市场 5923 只** ✓ |

⇒ 我们 5923 只里的绝大多数，他**连候选都没有**；反过来，他那 200 只（涨幅榜）本身就**偏向小盘低价票**。

### 2) 评分公式有字段误用 —— 他的"高分"大半是恒定项顶上去的

复刻 `computeScore` 时发现（原文照抄即可复现）：

| 位置 | 问题 |
|---|---|
| `circMV = parseFloat(stock.f10)` | 东财 `f10` 是**量比**，不是流通市值（市值是 `f20`）✗ ⇒ `marketScore` 恒为 1.0（量比永远 <30）|
| `getBidTurnover` 分母 `mv*100` | 用**量比**当市值做分母 ✗ ⇒ 结果异常放大 ⇒ `activityScore` 几乎恒为 1.0 |
| `getBidVolumeRatio` | **恒返回 0** ⇒ 量比加分是死分支 ✗ |
| `priceGt: 30` 的判据 | `if (price > 30) return false` ⇒ 实际是**剔除 >30 元的票**（注释写的像"筛价格>30"）✗ 语义反转 |
| `floatMvGt: 100` 的判据 | 比较的是 `f10`（量比）⇒ `量比>100` **永不触发** ⇒ 死规则 ✗ |

**后果（实测）**：他给的"95 分""93 分"，是把 `activityScore`(权重 0.32) 与 `marketScore`(0.11) 两项**钉在满分**（合计权重 0.43）后的产物；
用**正确口径**（市值用 `circ_mv`、换手用我们 9:25 竞价换手）重算他那 113 只 ⇒ 分数只有：

```
20~29分: 63 只 | 30~39分: 36 只 | 40~49分: 9 只 | 50~59分: 5 只
```

而他名单的**真实画像**（用我们库的口径看）：
- 竞价涨幅 **-9.2% ~ +4.1%（均值 +0.2%）** ⇒ 以**低开/平开**为主，不是"竞价强势"票
- 竞价成交额 **2 ~ 8444 万（均值 524 万）** ⇒ 与我们「竞价额≥1000 万」门槛大量冲突
- 流通市值 **8 ~ 426 亿（均值 49 亿）** ⇒ 跨度极大（含 8 亿小票）

### 3) 数据时刻不同

| | 他 | 我们 |
|---|---|---|
| 数据 | 浏览器**直连东财**当前快照 | **9:25 定格**快照落库（`features`）|
| 可回看历史 | ✗（周末拿到的是上一交易日口径，`f615` 会缺失/退化）| ✓ 全历史可回放 |
| 可评估/可训练 | ✗ | ✓（走前向、影子、闸门都在此之上）|
| 手机端风险 | CORS / 限流 / 字段变更 ✗ | 服务端代理 ✓ |

## 三、可行性判断

**问题：前端和后端都只用这个页面的数据，是否可行？**

| 方案 | 判断 | 原因 |
|---|---|---|
| 完全照用（东财直连 + 该公式 + 涨幅榜 200）| **不可行/不建议** ✗ | 候选池缩到 1/30；评分未经验证且字段误用；丢掉 9:25 定格、历史回看、评估/影子、自选池、配额、四线名单 |
| 用它的**数据源**（东财行情）| **部分可行** ✓ | 我们本来就用东财做"现涨 merge" ✓，但必须**服务端代理 + 落库**（不能浏览器直连）|
| 用它的**视觉/版式与交互** | **可行且推荐** ✓ | 勋章卡 Top 榜、大标题、可折叠筛选条 —— 纯展示层，零风险 |
| 用它的**经验参数**（如"竞价涨幅 3~5.5% 最优"）| **需回测验证** ✓ | 可以把它这套评分当排序器，跑 133 天走前向评估，用数据判断有没有信息量 |

1. 本对比用的是**只读脚本复刻**（脚本文本见 `/tmp/kx_v3/cmp4.py`、`/tmp/kx_v3/overlap2.py`），未改任何产品代码与数据 ✓
