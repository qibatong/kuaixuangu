## 四、根因

`ai_predict._market_prob_map(date)` 的设计是**全市场概率图，当日缓存一次**：

```python
def _market_prob_map(date):
    """全市场 {code: 涨停概率}。当日缓存一次推理"""
    rows = collector.fetch_from_kuaixuan(date)   # 全市场 5923 只 + 猫爪补字段 5561 只（出网）
    df = pd.DataFrame(rows)                       # pandas（首次 import 还要 ~1.8s）
    model.predict_proba(...)                      # 全市场推理
```

而它被 `/api/stock/detail` 调用 —— **为了给 1 只票算评分，拉全市场 + 出网 + 全市场推理**。

**为什么用户经常撞上**：缓存是**进程内**的，且**按日期**失效 ⇒
- 服务重启后冷
- **每天第一个打开详情的用户**必然冷（要替全体等 5 秒）

## 五、修复：预热（不改评分口径）

**没有选择**"加超时降级"那条路 —— 那会让异动分走 default、**悄悄改变评分结果**。
采用项目已有范式（`main.py` 里昨比 / spotMap / KPL 首屏都有同款预热）：

```python
# ai_predict.py 新增
def warm_market_prob(date=None) -> int     # 把全市场概率图算出来写进进程缓存
def start_ai_prewarm()                      # 幂等的后台线程（每 60s 检查，按日重预热）
```

```python
# main.py 的 on_startup 里挂载（与其它预热同款 try/except 契约：失败绝不影响主服务）
try:
    from .services import ai_predict as _ai
    _ai.start_ai_prewarm()
except Exception as e:
    log.warning("AI概率图预热启动失败(不影响主服务) err=%s", e)
```

**必须挂 web 进程**：`_prob_cache` 是**进程级**的，`kx-worker` 预热不共享（与昨比预热同因）。

### 效果实测

```

② 预热后首次 B.load([code])   0.277s   ← 从 5.5s 降下来
③ 再开一只票                  0.260s
④ 再开一只票                  0.263s
```

**⇒ 用户侧：5.5s → 0.28s（约 20 倍）**

## 六、`/api/chaozhi/overview` 也在慢（主人指示继续排查 → 已修复）

```
/api/chaozhi/overview    66 次   平均 2.32s   中位 2.64s   最大 3.77s   49/66 次 >2s
```

超智页本身的聚合接口**平均 2.3 秒**，且 **74% 的请求都超过 2 秒**——这不是偶发冷启动，是**常态慢**。

### 排查：9 个串行环节，单看都不慢，串起来就 2 秒+

```
① score_emotion()          0.292s     ⑥ support_today()        0.002s
② score_capital()          0.258s     ⑦ load_picks()           0.300s
③ score_promote()          1.332s ←   ⑧ load_shadow()          0.492s
④ load_emotion_series()    0.006s     ⑨ load_hit_series()      0.909s ←
⑤ load_capital_series()    0.279s
★ 完整 _build()（热态）     1.762s     （冷态合计 ≈3.9s）
```

**根因不在某个环节，而在"串行 × 缓存窗口太短"**：

- `_build()` 是 9 个**串行**步骤，冷算 1.8~3.9s
- 缓存 TTL 只有 **60 秒**
- 日活用户少 ⇒ **每个 TTL 周期后的第一个请求都要重算**，命中率极低

### 修复：同款预热（TTL 60s : 预热 30s = 2:1）

```python
# chaozhi.py
OVERVIEW_PREWARM_SEC = 30
def start_overview_prewarm():        # 后台线程每 30s 走一次带缓存的入口
    ...
```

```python
# main.py on_startup
try:
    from .services import chaozhi as _czh
    _czh.start_overview_prewarm()
except Exception as e:
    log.warning("超智聚合预热启动失败(不影响主服务) err=%s", e)
```

**效果实测**：

```
第1次 build_overview()   0.002s
第2次 build_overview()   0.002s     ← 从平均 2.32s 降下来
第3次 build_overview()   0.003s
缓存 chaozhi:overview 命中: True (11566 字节)
```

**⇒ 超智页聚合接口：2.32s → 0.002s**

## 七、两个问题的共性与本次修复的共同点

| | 个股详情 | 超智聚合 |
|---|---|---|
| 慢的原因 | 单只票触发**全市场**推理（出网 + 全市场 predict） | **9 个串行环节** × **60s 短缓存窗口** |
| 冷算耗时 | 5.0s | 2.3s（冷态 3.9s） |
| 修复手段 | **预热**（后台线程，60s 一轮） | **预热**（30s 一轮） |
| 修复后 | **0.28s** | **0.002s** |

**共同的判断**：两次都**没有选择"加超时降级"** —— 那样会让评分静默走默认值、悄悄改变结果。
以"后台预热保持缓存常热"解决，**用户侧变快，数据口径一字未改**。

**共同的前提**：缓存都是**进程级/短 TTL**，而 `kx-worker` 是独立进程、预热不共享 ⇒ **必须挂 web 进程**。
