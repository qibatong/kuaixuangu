## 0. 一句话结论（先说推翻了什么）

上一轮我提的「① seal + net 合并成一次批量拉取」——**应砍掉，收益≈0**。

理由（生产实测 + 仓库内既有实测结论，两处互相印证）：

- 竞价窗口内，榜单接口 `MorningBiddingList` 每次出网只有 **1~2 次**
  （日志：`MorningBiddingList|T4=1`），合并两个 Type 顶多省 1 次。
- 仓库 `kpl.py:2369-2371` 早已写下实测结论：
  「封单 tab 冷启 66 次（其中 `GetStockIDPlate` 60 次 + 榜单 7 次）；

**真正的成本是按股概念 `GetStockIDPlate`**，而且我发现了一个此前没被定位到的放大器：

> `clear_cache()` 用 `store.clear_prefix("kpl:")` **无差别清空全部 kpl 缓存**，
> 把本该跨枪复用（TTL 1h）的按股概念池 `kpl:concept_deep` 一起清掉了。
> 竞价窗口内它被调用 **4 处 × 多时点**，每次都把池打回冷态。

## 3. P0：`clear_cache()` 语义收窄（核心项）

### 3.1 为什么这样改（不改签名）

`clear_cache()` 在生产有 **4 处**调用，意图**全部一致**——都是为了拿新鲜的竞价数值：

| 位置 | 上下文 |
|---|---|
| `auction_snapshot.py:821` | 竞价委买榜 fallback 前 |
| `auction_snapshot.py:1193` | 时点快照叠加前（注释「保证拿到当前时点的新鲜数据」） |
| `auction_snapshot.py:2506` | 抢筹结果快照前 |
| `auction_snapshot.py:2539` | 竞价异动落库两枪前（注释「两枪都必须拿此刻的开盘啦最新值」） |

**没有任何一处是要清概念的。**

所以采用**收窄语义、不改签名**的方案：

- 生产 4 处调用点 **一行都不用改**
- 测试里 9 处 `monkeypatch.setattr(kpl, "clear_cache", lambda: None)` **零影响**
  （若改成 `clear_cache(scope)` 加参数，这些 `lambda: None` 会 `TypeError`，
  需同步改 9 处测试文件——收窄方案规避了这整块风险）

### 3.2 改动

**文件**：`backend/app/services/kpl.py`
**位置**：`127-132` 行

**改动前**：

```python
def clear_cache():
    """清空全部 KPL 缓存(快照采集前强制拿当前时点新鲜数据)"""
    try:
        store.clear_prefix("kpl:")
    except Exception:
        pass
```

**改动后**：

```python
# 🔴 2026-10-09 竞价链路: 概念类缓存**不得**随数值榜单一起清。
#   `kpl:concept_deep` 是按股概念共享池(TTL 1h; 概念归属日内稳定, 见 fetch_board_map
#   注释「概念归属日内稳定」)。原实现 clear_prefix("kpl:") 无差别全清 ⇒ 竞价窗口内
#   4 处调用(9:15/9:20/9:24/9:25 时点叠加 + 抢筹 + 落库两枪)每次把池打回冷态
#   ⇒ 前台每轮现查 60~98 只, 撞满 3s 概念预算 ⇒ /api/kpl/bid-seal 实测 4.9~9.8s,
#     概念残缺转后台补齐。生产实测 09:16 单 60s GetStockIDPlate=118 次。
#   4 处调用者意图一致(拿**新鲜竞价数值**) ⇒ 收窄本函数语义即可, 不动调用点与签名。
_BID_NUMERIC_KEYS = (
    "kpl:bid_seal",              # MorningBiddingList Type4 竞价委买
    "kpl:bid_net",               # MorningBiddingList Type2 竞价净额
    "kpl:bid_boom_ratio_v3",     # 竞价爆量(量比榜, 库内算但依赖当日快照)
)
# 概念类(保留, 不随数值清): kpl:board_map(榜单概念, TTL 300s) / kpl:concept_deep(按股, TTL 1h)

def clear_cache():
    """清空**竞价数值类** KPL 缓存(快照采集前强制拿当前时点新鲜数据)

    2026-10-09 收窄: 只清数值榜单, 保留概念类 —— 详见上方 _BID_NUMERIC_KEYS 注释。
    需要全清(如排查/数据订正)时调 clear_cache_all()。"""
    try:
        for _k in _BID_NUMERIC_KEYS:
            store.delete(_k)
    except Exception:
        pass


def clear_cache_all():
    """全清 kpl: 前缀缓存(原 clear_cache 行为)。当前生产无调用方, 仅供排查/订正用。"""
    try:
        store.clear_prefix("kpl:")
    except Exception:
        pass
```

### 3.3 影响面

- **出网**：竞价窗口 `GetStockIDPlate` 预期从 118 次/60s 降到个位数~几十
  （池跨枪复用，只有**当天新票**才现查）
- **接口耗时**：`/api/kpl/bid-seal` 消除 3s 概念阻塞，预期 4.9~9.8s → <2s
- **展示**：概念完整性提升（不再「转后台补齐」）
- **数据正确性**：**不变**。概念归属日内稳定，跨枪复用是正确行为；
  数值榜单照旧每枪强制刷新，两枪语义（09:24 保底 / 09:25:35 覆盖拿净额）**完全保留**

### 3.4 风险与回滚

| 项 | 说明 |
|---|---|
| 风险 | 低。不改签名、不改调用点、不改任何取数口径 |
| 副作用 | 若某场景依赖「清概念」来纠正错误概念 → 无此场景（概念 TTL 1h，日内稳定） |
| 回滚点 | 单文件单函数，`git revert` 即可；无 DB 变更、无迁移 |
| 兜底 | 万一需恢复原行为：把 4 处调用改调 `clear_cache_all()` |

## 4. P1：`bid-net` / `bid-boom` 补接口级缓存

### 4.1 现状

| 接口 | 服务层缓存 | 接口层缓存 |
|---|---|---|
| `bid-seal` (`api/kpl.py:302`) | `_cached("bid_seal", 30s)` | ✅ 竞价 15s / 盘后 300s / 历史 600s（`:364`） |
| `bid-net` (`:417`) | `_cached("bid_net", 30s)` | ❌ **无** |
| `bid-boom` (`:367`) | `_cached("bid_boom_ratio_v3", 30s)` | ❌ **无** |

⇒ 每次请求都要重跑「fill 补齐 + 概念覆盖 + `_boom_spot_map` 东财点查」。

### 4.2 改动

照 `bid-seal:364` 的同构写法，给两个接口加 `cached_singleflight`：

```python
# api/kpl.py bid-boom (367) 与 bid-net (417) 末尾, 由
#     return jr({"ok": True, "list": d, "count": len(d)})
# 改为套一层 cached_singleflight(store, ck, 15 if auction else 300, _load)
```

缓存键与 TTL 与 `bid-seal` 对齐：
- 实时模式：`bidboom:live` / `bidnet:live`，TTL **15s**（竞价时段）
- 盘后：`bidboom:post` / `bidnet:post`，TTL **300s**
- 历史日：`bidboom:hist:<date>` / `bidnet:hist:<date>`，TTL **600s**

### 4.3 影响面 / 风险 / 回滚

- 收益：省重复重算与东财点查；**不省出网**（boom 出网本就是 0）
- 风险：低，纯只读缓存；口径不变
- 注意：`boom` 的 `_boom_spot_map` 实时涨幅会随缓存被「冻结 15s」，与 seal 现行行为一致
- 回滚：单文件 `git revert`

## 5. P2：`boom` 单枪化（挪到定格后）

### 5.1 依据

`fetch_bid_boom()` 是**纯库内算**（`_boom_from_snap` 读 `snapshot_bid` 今日 vs 昨日 9_25），
**不依赖「开盘啦 09:25:30 出净额」这个约束**，却被绑在两枪里各算一次
（今日 33 → 36 只，差异很小）。

### 5.2 改动

`kpl.py:4745-4750` 的 `items` 列表加 `phase`/`shot` 参数控制：

- 第一枪（09:24）+ 第二枪（09:25:35）：只落 `seal` / `bid_net` / `qiangcang`
- **定格后（09:26:30）** 单独落 `boom`，此时 `snapshot_bid` 9_25 已定格，算出来最准

### 5.3 影响面 / 风险

- 收益：省一次全市场自算 + 一次东财点查；且定格后算更准
- 风险：低。但需确认「定格后落 boom」的调度落点已存在（9_26 时点已有调度）
- ⚠️ 待确认：`snapshot_bid` 的 9_25 行在 09:25:35（第二枪时）是否已写入完整
  —— 若未写入，第二枪的 boom 反而不准，这正支持「挪到定格后」

**建议**：要么不动；要么改成「serveDate 随当前 tab 响应一并返回」，省一次 RTT 但不降频（更优，但改动更大）。
