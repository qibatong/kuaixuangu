# 站内「系统消息」方案（2026-10-04）

主人原话：「系统消息比如**系统更新提醒，会员到期提醒**，等等」

## 一、先分两类——成本差一个数量级

| 类别 | 例子 | 数据从哪来 | 要不要新表 |
|---|---|---|---|
| **A. 站方广播**（人工发布） | 系统更新提醒、停服维护、新功能上线 | 管理员在后台发 | 🔴 **要**：`notices` 表（现在没有） |
| **B. 账户事件**（实时推导） | 会员到期、试用将尽、每日次数用尽 | `users.expire_at` / session / usage | **不要**：纯函数算，零存储 |

**B 类已经有一半了**：`MemberView.vue` 早就有「会员将在 N 天后到期」提醒条（≤3 天触发），
数据现成、不需新表 ⇒ 只要把它**聚合进消息中心**即可，成本极低。
真正要新建的是 **A 类**。

⚠️ 别复用 `services/notify.py`：它是**对外**推微信/飞书群机器人（选股结果），
是站方→群，不是站方→某个用户；混进来会把它改坏。

## 二、数据结构（最小够用）

```sql
CREATE TABLE notices (
  id          INTEGER PRIMARY KEY,
  title       TEXT NOT NULL,
  body        TEXT NOT NULL,
  level       TEXT NOT NULL DEFAULT 'info',   -- info / warn / urgent（urgent 强弹一次）
  target      TEXT NOT NULL DEFAULT 'all',    -- all / member / vip / free（按会员等级定向）
  start_ts    INTEGER NOT NULL,               -- 生效时间（可预约未来发布）
  end_ts      INTEGER NOT NULL DEFAULT 0,     -- 0 = 长期有效；到期自动不再返回
  created_by  TEXT,
  created_at  INTEGER NOT NULL
);
CREATE TABLE notice_reads (                   -- 已读回执（跨设备同步才需要）
  user_id   INTEGER NOT NULL,
  notice_id INTEGER NOT NULL,
  read_at   INTEGER NOT NULL,
  PRIMARY KEY (user_id, notice_id)
);
```

## 三、接口

| 接口 | 说明 |
|---|---|
| `GET /api/notices` | **聚合返回**：A 类（按 target 过滤 + 有效期内）+ B 类（实时算：到期天数/次数）统一成 `{id,type,level,title,body,ts,read}`；同时返回 `unread` 数 |
| `POST /api/notices/read` | 已读回执（body: `{ids:[...]}` 或 `{all:true}`） |
| `GET /api/admin/notices` / `POST /api/admin/notices` / `POST /api/admin/notices/off` | 管理端：列表 / 发布 / 撤回（挂 `admin.py`，那里已有 25 个接口，`AdminView.vue` 加一张「公告」卡） |

## 四、前端

- 顶栏**右上角铃铛** + 未读红点（数字）；手机端并入顶栏三栏改造（左头像 / 中搜索 / 右消息）
- `/messages` 消息中心页：A 类按时间倒序；B 类（账户事件）置顶且**不落"已读"**（它是状态，读不掉，条件消失才消失）
- 轮询：复用现成的 `setInterval` 模式；`urgent` 级进来时**强弹一次**（同 id 只弹一次，存 localStorage）

## 五、工作量

| 项 | 人日 |
|---|---|
| 后端：两张表 + 迁移（两机各一次） | 0.5 |
| 后端：`/api/notices` 聚合（A 过滤 + B 推导）+ 已读接口 | 0.8 |
| 后端：管理端 发布/列表/撤回 3 接口 | 0.5 |
| 前端：铃铛 + 红点 + 轮询 + `/messages` 页 | 1.0 |
| 前端：手机端顶栏三栏（头像/搜索/消息） | 0.5 |
| 管理端 UI（AdminView 公告卡） | 0.5 |
| 守卫 + lint + 两机部署验收 | 0.5 |
| **合计** | **≈ 4.3 人日** |

**砍到 ≈2 人日 的 MVP**：只做 A 类（一张 `notices` 表 + 管理端发布 + 铃铛/消息中心），
已读状态存 **localStorage**（不要 `notice_reads` 表），会员到期**继续留在 `/member`**（已有提醒条），
顶栏三栏改造单独排。

## 六、🔴 需要主人拍板（不定我不动手）

1. **已读要不要跨设备同步**：服务端 `notice_reads` 表（+0.3d，换手机不重弹）vs localStorage（省事，换设备会重弹）
2. **定向粒度**：全员 + 按会员等级（建议）／要不要再支持**指定单个用户**（催续费场景；+0.3d）
3. **到期提醒要不要主动找人**：只在站内红点（最省）／还是顺带推微信（现有 Server酱 渠道，但要给每个用户绑 SendKey，+1d 且要用户授权）
4. **先做哪个**：直接做完整版（≈4.3d）／先 MVP（≈2d）看效果再加
5. **消息留多久**：建议 A 类只返回最近 30 条 + 有效期内，表不清理（量极小）

## 七、与「安卓 APK」的关系

APK 只做展示（不上架、不内购）⇒ 消息中心在 APK 里就是同一个 `/messages` 页，**零额外成本**；
若将来要**推送到手机通知栏**，那是另一件事（要 FCM/个推 + 国内机型适配，1~2 周），本次不做。
