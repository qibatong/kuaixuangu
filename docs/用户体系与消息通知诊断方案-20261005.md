# 快选股 · 用户管理后台 & 消息通知体系 全面诊断与建设方案

> 诊断日期：2026-10-05 ｜ 诊断对象：www.kuaixuangu.cn（竞价选股工具站）
> 结论基于对仓库前端 `frontend/src` 与后端 `backend/app` 的**实际代码审查**，非通用模板。
> 本文档为**方案**，不含代码改动；落地前需逐项确认（详见文末「六、待确认事项」）。

## 〇、诊断前提：先定义快选的用户行为模型

**这条决定了整个消息体系该怎么建，抄同花顺会抄错。**

| 维度 | 同花顺 / 雪球（持仓型） | 快选（时点型） |
|---|---|---|
| 用户打开时机 | 全天、碎片化、随时看 | **集中在 9:15–9:35 这 20 分钟**，其余时间基本不打开 |
| 核心资产 | 持仓、自选股、账户盈亏 | 每日一份「9:25 竞价名单」 |
| 消息的作用 | 拉活（全天多次打扰） | **在对的 20 分钟前把人叫回来**（一天最多 2–3 条） |
| 消息失败后果 | 少看一次资讯 | **当天产品价值归零**（名单过期了） |

**由此得出的三条铁律：**

1. **快选的消息必须「按时点编排」，不是「按事件触发」。** 最有价值的消息不是"某只股票涨了"，而是「9:15 竞价开始了」「9:26 今日名单已出，共 N 只，最高分 XX」。前者是同花顺逻辑，后者才是快选逻辑。
2. **消息的商业 KPI 是「9:15–9:35 在线率」+「到期前 7 天续费率」，不是打开率。** 高频打扰在快选是负资产（一天超过 2 条就会被关推送，而推送是当前唯一的站外触达通道）。
3. **付费转化全靠微信人工**，因此消息体系必须做到：**用户不在站内时也能被触达 → 带着"我是谁"回到微信 → 客服能秒懂是谁要续费**。目前这条链路断在最关键的一环（见下）。

**三条收入链路与各自的消息断点：**

| 收入链路 | 现状断点（代码级证据） |
|---|---|
| 注册 → 试用 → 付费 | 免费用户 `picker` 3 次/天用完后是硬 429（`deps.py:122-136`），**此刻转化意愿最高，却没有任何消息或引导** |
| 到期 → 续费 | 到期提醒是 `GET /api/notices` 时**实时推导**的 account 类消息（`notices.py:111-184`），**不落表、不推送** ⇒ 用户不进站就永远看不到 ⇒ 续费只能靠用户自己记得 |
| 邀请 → 送天数 | 邀请成功**没有任何通知**（`invite.py` 无消息写入），邀请人不知道自己赚了 5 天，正反馈循环断了 |

**一句话诊断：快选已建好了"消息的技术管道"（WebPush 订阅表 `push_subscriptions` 已建、`notice_reads` 回执、红点、定向发布、撤回全都有），但还没有"消息的内容与运营"。管道是空的——目前站内公告发布数为 0，WebPush 订阅数为 0。**

## 二、消息通知体系（/messages + 推送链路）

### 2.1 现状问题速览（代码级）

| 现状 | 证据 | 影响 |
|---|---|---|
| **无分类**，两类消息混排 | `MessagesView.vue:49-72`，broadcast/account 靠 tag 区分 | 用户找不到"上次那条会员提醒"；运营消息与系统消息同权重 |
| **无单条删除** | 只有「全部已读」（L24, 156-170） | 过期消息永久堆积（如已过期的活动），列表很快变噪音 |
| **account 类不能标已读**（`nid=0`、`read` 恒 0） | `notices.py:217` 附近，文件头注释 L6-10 | 设计上有道理（它是"状态"不是"信件"），但导致**无法统计"到期提醒有多少人看过"** ⇒ 运营盲区 |
| **红点规则偏保守**：account 的 info 级不计数 | `notices.py:220-222` | 合理，但**反过来说 info 级运营消息永远激不起红点**，等于白写 |
| **WebPush 订阅数 0，站内公告发布数 0** | 生产库实测 | 管道建好了但从未使用；**首次推送的文案与频次直接决定这个通道的生死** |
| **安卓环境整个推送入口隐藏** | `usePush.js:41-46`（FCM 国内不可达） | 安卓用户（国内主力）**完全没有站外触达能力** ⇒ 安卓侧必须靠微信/短信补位，不能押注 WebPush |
| **无触达统计**：不知道送达多少、打开多少 | `notice_reads` 全库仅 4 处引用，admin 列表不返回已读数 | 运营无法评估公告效果，只能凭感觉 |
| 🔴 **`notices.id` 无 AUTOINCREMENT，id 会复用** | `database.py:772` + `admin.py:1453-1458` 注释 | **这是所有新增能力的硬前置**：要做单条删除/编辑/触达统计/消息详情，必须先解决 id 唯一性，否则统计会串到新行上。当前靠"发布时 `DELETE FROM notice_reads WHERE notice_id=?`"自愈，属于补丁 |

## 四、优先落地路线图

### 第一批（先做这 5 件）—— 目标：把空管道接通，把最近的钱捡起来

| 顺序 | 事项 | 理由 |
|---|---|---|
| **1** | **M1 消息 id 唯一化**（技术前置） | 不做这个，后面所有涉及"删除/编辑/统计"的能力都会踩 id 复用的坑（历史上已经因此出过"红点永不亮"的生产事故）。量级小，但不做会持续付出调试成本 |
| **2** | **U2 + A3 到期续费闭环**（用户端四级触达 + 后台一键批量提醒） | **离钱最近**。当前到期提醒只在站内、不落表、不推送，是三条收入链路里最明显的漏洞；且实现只需"定时扫 `expire_at` + 复用现有 account 消息机制 + 后台加批量按钮"，投入产出比最高 |
| **3** | **U1 竞价闹钟 + 名单就绪推送** | **这是快选区别于所有同类产品的消息**，也是唯一能真正提升"9:15–9:35 在线率"的手段。已有 `wpqc_push` 的 14:57 定时推送骨架可直接复用，边际成本低 |
| **4** | **U3 配额耗尽转化卡** | 量级最小（429 分支插一条写入 + 改文案），但抓的是**转化意愿最高的瞬间**。同批还能产出"每天多少人撞免费墙"这个关键运营指标 |
| **5** | **U4 + M4 订阅偏好中心**（含 M2 分类、M3 单条管理） | 必须在**大规模推送开始之前**就位。否则第一波推送一旦打扰到用户，用户唯一能做的就是关掉总开关，站外通道永久失效。顺序上不能晚于 U1 上线 |

> **为什么这 5 件的排序是这样**：1 是地基，2 捡钱，3 兑现产品核心价值，4 抓转化窗口，5 保护通道。**第 5 件必须在第 3 件之前或同步完成**——先推后给开关，等于逼用户关推送。

### 第二批（再做这 5 件）—— 目标：从"能发消息"进化到"发得准、知道效果"

| 顺序 | 事项 | 理由 |
|---|---|---|
| **6** | **A1 公告定时/草稿/编辑 + A5 发布预览** | 第一批跑通后，运营的第一个抱怨一定是"我还得 9:25 手动蹲点发"。定时是把运营从执行里解放出来的关键 |
| **7** | **M6 + A2 触达漏斗（送达/已读/点击）** | 没有数据就无法优化。跑了一个月推送还不知道已读率，等于盲飞 |
| **8** | **U5 邀请成功通知 + U6 签到增强** | 这两件都是"简单"量级，且分别补上裂变正反馈和非交易日回访理由，是低成本的留存杠杆 |
| **9** | **A4 用户分层标签 + A7 导出扩充 + A10 转化漏斗** | 让"微信人工转化"可度量、可定向。其中 A7 最简单（导出名单就是客服的工作清单），可先做 |
| **10** | **U7 自选池告警**（或 U8 会员价值回顾，二选一先做） | 两者都是复杂/中等的"提升留存厚度"型功能。**建议先做 U8**：它直接服务续费话术，且依赖的 `usage_daily` 数据已在库里，比告警系统（需新增规则表+盘中扫描+去重）风险低得多 |

### 暂缓 / 需要重新评估的

- **M10 安卓推送补位**、**U9 微信客服绑定**：这两件决定"站外触达能不能覆盖安卓用户"（国内主力）。**技术上不难，但需要业务决策**——微信侧要不要投入人工/半自动运营？短信成本谁承担？建议第一批上线后用真实数据（安卓用户占比、WebPush 订阅率）再决定投入。
- **M11 邮件渠道**：除非做"盘后复盘日报"，否则对日内时点工具价值很低，P2 可长期不动。
- **U13 设备管理**、**U12 换绑手机号**：体验完整性项，无直接商业价值，可在有余力时补。

## 五、三条必须写进开发规范的硬约束（来自本仓库的历史事故）

1. **任何涉及 `notices` 表的新能力（删除/编辑/统计），必须先确认 id 唯一性已解决**（`database.py:772` 的 `INTEGER PRIMARY KEY` 无 AUTOINCREMENT，DELETE 后 id 复用，回执会错挂）。
2. **account 类消息（到期提醒等）目前 `nid=0`、不可标已读**。若要统计"到期提醒触达率"，必须改成落表并分配真实 id，否则 `notice_reads` 永远记不到它。
3. **推送频次上限必须写死在代码里**（建议：同一用户同一天最多 3 条，其中运营类最多 1 条）。快选是时点型工具，用户容忍阈值远低于同花顺/雪球；一次过度推送会导致永久关闭权限，而这个权限目前是**唯一的站外通道**。
