## 一、祖本取数方式：单文件 HTML，浏览器直连东财，全站只有一个出口

### 1.1 唯一的接口

```js
https://push2dycalc.eastmoney.com/api/qt/clist/get
  ?fs=<勾选板块>&fltt=2&invt=2
  &fields=f2,f3,f4,f5,f6,f8,f10,f12,f14,f17,f18,f20,f615,f630,f100,f102,f103
  &fid=f3&po=1&pn=1&pz=200&np=1
  &ut=c92c50e6b0fab2c17cd5e276e9a79c42
```

| 参数 | 值 | 含义 / 影响 |
|---|---|---|
| 调用点 | `fetch` 仅 **2 处** | ① 首次选股 ②「只刷实时涨幅」 |
| `fs` | `m:1+t:2,m:0+t:6` | 沪主板 + 深主板；勾选创业板 → `m:0+t:80`，科创板 → `m:1+t:23` |
| `fid=f3&po=1` | 按**当日涨跌幅降序** | 🔴 决定拿到的是哪 200 只 |
| `pn=1&pz=200` | 第 1 页、200 只 | 🔴 **只取"涨幅前 200 名"**，无分页、无后端 |
| `ut` | 写死的公开 token | 与东财网页版同款；**不带 `_=` 破缓存参数** |
| 兜底源 | **零** | grep 腾讯 / 新浪 / 开盘啦 / 同花顺 = 命中 **0** |

### 1.2 三个直接后果

1. **覆盖被锁死在 200 只**：不在"涨幅前 200"里的票**永远不可能被选出**。这是祖本最大的覆盖缺陷。
2. **无服务端**：数据、打分、筛选、锁仓全在浏览器里。刷新即重算。
3. **无兜底**：东财一挂就是白屏，没有任何降级路径。

> 快选已改掉后两点（服务端全市场分页 + 腾讯 GBK 兜底），第 1 点仍是当前架构与祖本的分野。

## 二、🔴 字段映射：祖本有一处硬伤（把 `f10` 当流通市值）

2026-09-19 实测钉死（浦发银行 / 白云机场 / 东风股份等，用 `f8` 与自算值的比值 **0.97~1.01** 交叉验证）：

| 字段 | 祖本当它是 | 实测真实语义 | 判定 |
|---|---|---|---|
| `f2` | 现价 | 最新价 | ✅ |
| `f3` | **"昨日涨幅"** | 🔴 **当日涨跌幅**（9:25 时 ≈ 竞价涨幅，与 34% 因子共线） | ❌ 语义错 |
| `f8` | 换手率 | 换手率(%) | ✅ |
| **`f10`** | **流通市值** | 🔴 **量比**（实测 0.74~0.95） | ❌ **硬伤** |
| `f20` | 总市值 | 总市值 | ✅ |
| **`f21`** | 未使用 | ✅ **才是流通市值**（单位：元） | 漏用 |
| `f615` | 竞价涨幅 | 竞价涨幅(%) | ✅ |
| `f630` | 异动等级 | 异动等级（枚举 0~14） | ✅ |
| `f100/f102/f103` | 行业/地区/概念 | 同 | ✅ |

### 2.1 硬伤 `f10` 引发的连锁后果（三个叠加）

祖本代码：`marketScore = mv < 30 ? 1 : …`，`bidTurnover = f5*f2/(f10*100)`，筛选 `mv > floatMvGt`。

1. `mv = f10 ≈ 0.74`（量比）→ 恒 `< 30` → **11% 流通市值因子恒满档 1.0**
2. `bidTurnover` 实测 ≈ **63460** → 恒 `≥ 0.8` → **32% 换手率因子恒满档 1.0**
3. `mv > floatMvGt` **永不成立** → **市值筛选形同虚设**

⇒ **祖本 43% 的打分权重（11% + 32%）是常数**，真正参与排序的只有
**竞价涨幅 34% + 异动 17% + 昨日涨幅 6% = 57%**。

> ⚠️ **这类 bug 的形态**：页面照常显示、列表照常有结果、没有任何报错。**静默失效**。

### 2.2 快选已修正这个坑（这是"修好后才真正生效"的因子）

| 项 | 祖本 | 快选现状 | 结论 |
|---|---|---|---|
| 换手率来源 | `f5*f2/(f10*100)`（量比当流通市值） | `f8`（`picker/contract.py`） | ✅ 已修 |
| 流通市值来源 | `f10`（量比） | `f21`（`auction_snapshot`） | ✅ 已修 |
| 负竞价涨幅 | `else 0.1`（与"数据缺失"同分） | 独立 **0.05 桶** | ✅ 已修 |
| 档位表 | `5→1.0 / 4→0.85 / 3→0.6 / else 0.18` | **逐字一致** | 继承 |
| 权重 | `0.34/0.32/0.17/0.11/0.06` | **逐字一致** | 继承 |

⇒ 快选的 32% 换手率与 11% 市值因子，是**修好之后才第一次真正参与排序**的，
不是从祖本"继承"来的能力。**理解这一点，才能正确理解这两因子的历史表现基线。**

## 三、17% 异动因子的血缘铁证：它就是 `f630`

代码级对照（快选 `backend/app/services/scorer.py`）：

```python
# 祖本 (JS)
warnScore = warnType === 5 ? 1 : warnType === 4 ? 0.85 : warnType === 3 ? 0.6 : 0.18

# 快选 (Python)
factors.warn.buckets = [["5", "6", 1.0], ["4", "5", 0.85], ["3", "4", 0.6]]
factors.warn.default  = 0.18
weight                = 0.17
```

**档位、默认值、权重三者逐字一致** ⇒ 17% 因子的语义在祖本时代就已确定。

### 3.1 由此得到的关键结论

> **`f630` 一直是"能取到"的。** 祖本在浏览器里直连同一个 clist 接口，`fields` 里就写着 `f630`，
> 页面据此打分。

⇒ 因此 2026-09-17 那场"17% 因子全员失效"事故，**根因在快选的采集落库环节，不在数据源**。
（详见 `docs/history.md` v4.11.30 条目：采集只落 8 列，`f630` 被静默丢弃 →
定格链路 `warn_type=None` → 全员落 `default 0.18` → 概率天花板 99.4 崩到 85.5 →
被 `scoreFloor=80` 压成空名单。）

## 五、由祖本引出的架构选项：用户端本地取前 200 计算

> **提案原文**：「就用这个原始老师，让用户端本地取前 200 来计算，这样就没任何限流问题。」

这一节的目的是把它评估清楚 —— **支持的地方据实说支持，代价的地方据实说代价。**

### 5.1 实测：CORS 完全开放（技术上零障碍）

2026-09-19 12:20 于测试环境实测 `push2dycalc` clist，带不同 `Origin`：

| 请求 Origin | 东财回 `Access-Control-Allow-Origin` | `Allow-Credentials` |
|---|---|---|
| `https://kuaixuangu.cn` | `https://kuaixuangu.cn` | `true` |
| `https://www.kuaixuangu.cn` | `https://www.kuaixuangu.cn` | `true` |
| `http://localhost:5173` | `http://localhost:5173` | `true` |
| `https://evil-example.com`（任意域名） | `https://evil-example.com` | `true` |
| `Origin: null` | `null` | `true` |
| **不带 Origin** | **`*`** | — |

⇒ **东财 clist 回显任意 Origin；不带 Origin 时直接给 `*`。**
⇒ **浏览器从快选域名直连东财，不存在 CORS 障碍** —— 这就是祖本能跑起来的根本原因。

### 5.2 实测：`f630` **能取到**，且前 200 里的密度**高于**全市场

| 口径 | 样本 | `f630` 非 0 | **≥3 档（真正高分档）** |
|---|---|---|---|
| **前 200（`fid=f3&po=1`，主板范围内）** | 200 | **107（53.5%）** | **95（47.5%）** |
| 沪深主板全体（**同口径对照组**） | 3487 | 1268（36.4%） | 1144（32.8%） |
| 全市场（含创业板/科创板/北交所） | 5917 | 2280（38.5%） | 2101（35.5%） |

前 200 的 `f630` 完整档位分布：
`{0:93, 4:66, 3:17, 2:7, 1:5, 5:3, 10:3, 9:3, 11:2, 12:1}`

**原因**：异动等级天然与涨幅正相关 —— 按涨幅降序取前 200，等于**主动把异动票捞到样本里**。

> ### ✅ 直接回答提案里的疑问
> **"字段异动取不到值了吧？"—— 恰恰相反：能取到，而且比同一范围内的全样本更密。**
> 前 200 的 ≥3 档占比 **47.5%**，是沪深主板全体 **32.8%** 的 **1.45 倍**（同口径对比）。
> 也就是说，**祖本那套"取涨幅前 200"的采样，恰好是异动因子的天然富集区。**

#### 5.2.1 顺带订正一处口径错配（2026-09-19 复测）

早前记录的「全市场 **5856 只**里 **1268 只**非 0（21.7%）」**是把两个口径混在了一起** ——
`1268` 是**沪深主板**（3487 只，36.4%）的非 0 数，被错配到了全市场总数上。
本次分板块全量复测的准确值：

| 板块 | 总数 | `f630` 非 0 | 非 0 率 | ≥3 档 |
|---|---|---|---|---|
| 沪市主板 | 1846 | 421 | **22.8%** | 323 |
| 深市主板 | 1641 | 847 | **51.6%** | 821 |
| 创业板 | 1452 | 777 | **53.5%** | 747 |
| 科创板 | 621 | 151 | **24.3%** | 133 |
| 北交所 | 357 | 84 | **23.5%** | 77 |
| **全市场合计** | **5917** | **2280** | **38.5%** | **2101** |

**两个副产品结论：**

1. **沪市票的异动覆盖率只有深市的一半不到**（22.8% vs 51.6%）—— 这是数据本身的特征
   （沪市大票多、波动小），不是采集缺陷。⇒ **"17% 因子是否正常"不能只看全市场平均。**
2. **没有任何一只返回 `-`** —— `f630` 在 clist 里**总是有值**（`0` 表示无异动），
   这从侧面确认了「`0` = 无异动」的语义。

### 5.3 实测：通路矩阵（哪个接口能拿 `f630`）

| 接口（**域名决定生死**） | 用途 | 实测结果 | `f630` |
|---|---|---|---|
| `push2dycalc…/clist/get` | 列表（祖本用的） | ✅ 通（HTTP 200，前 200 全返回） | ✅ **有值** |
| `push2dycalc…/ulist.np/get` | 按代码点查 | ✅ **通**（`rc=0`，6 只全返回，139ms） | ✅ **有值**（000001/300434/002584 均为 `4`） |
| `push2…/ulist.np/get` | 按代码点查（**`fetcher._ULIST_URL` 写死的域名**） | ❌ `RemoteDisconnected`（48ms 秒断） | — |
| `push2dycalc…/stock/get` | 单票详情 | ✅ 通（29ms） | ❌ 不返回该字段 |

> 🔴 **2026-09-19 17:30 重大订正**：本节原结论「`ulist.np` 被**接口级**封死 ⇒ 补丁源永久失效、
> 改特征也救不回来」**是错的**。错因 = **把"域名被封"误判成"接口被封"**。以下为订正后结论。

**三条硬结论（订正版）：**

1. **封的是「域名」，不是「接口」**：`push2.eastmoney.com` 整站 RST/`RemoteDisconnected`；
   **同一路径换 `push2dycalc.eastmoney.com` 立刻通**。原实测"换完整浏览器特征亦失败"
   之所以失败，是因为**域名根本没换** —— 特征换一百遍也救不了一个被封的域名。
2. **`f630` 不止列表接口给**：`ulist.np` 点查**同样返回 `f630`**（实测 000001 / 300434 / 002584 均为 `4`）。
   ⇒ `eastmoney_realtime` 补丁源**并未永久失效**，改域名即可恢复。
3. 旁证：`hot_rank.py:153-156` **早已**把 `push2dycalc` 版 `ulist.np` 排在**首选**（注释写着
   "push2dycalc … 测试机可用"）—— 这个知识**存在过**，只是**没有同步到 `fetcher`**。

### 5.4 代价清单（把打分整体搬到用户端）

| # | 代价 | 说明 |
|---|---|---|
| 1 | 🔴 **丢掉 9:25 定格** | `f630` 是**随时间演进**的（实测：9:15–9:25 前几乎全 0，9:25:09 后跃变为 `{0:381, 4:126, 3:43…}`）。用户端每次刷新重取 ⇒ **名单会漂**，"一次定生死"机制失效 |
| 2 | 🔴 **同一时刻不同用户名单不同** | 各自浏览器独立采样，无统一权威名单 |
| 3 | 🔴 **历史功能全失效** | 历史回看 / 自动应用 / 批次落库 / 审计，全部依赖服务端 `batches`+`batch_stocks` |
| 4 | 🔴 **算法暴露** | 打分权重、档位表全在 JS 里，竞品可直接读取（商业产品，~152 用户） |
| 5 | ⚠️ **双实现漂移** | 前端须复刻 5 因子权重 + `f630` 档位 + 涨幅桶 + 换手/市值档位 + 全部筛选条件；与后端 `scorer` 双份维护，**必然漂移** |
| 6 | ⚠️ **覆盖收缩** | 前 200 会漏掉"竞价涨幅高但当日涨跌幅不在前 200"的票 |
| 7 | ⚠️ **异常值污染头部** | 实测 `fid=f3` 降序**第 1 名是次新股**（`f3=177.74`、`f8=89.08`、`f615=-27.88`、`f630=12`）—— 无涨跌幅限制票会占据前排名额 |
| 8 | ⚠️ **排序键不等价** | `fid=f3`（当日涨跌幅）≠ `fid=f615`（竞价涨幅） |

> **关于第 8 点的诚实标注**：本次"`fid=f3` 前 200 vs `fid=f615` 前 200 交集仅 42 只"的对比
> **是在周六（非交易日）做的，会显著失真** —— 周六 `f615` 是上一交易日 9:25 的定格值，
> 而 `f3` 是上一交易日的收盘涨跌幅，两者天然不等。**交易日 9:25 时点 `f3 ≈ f615`**
> （最新价=竞价价、昨收相同），届时差异会大幅收窄。
> ⇒ 该数据**只作方向性提示，不能作为结论**。真要定论须在交易日 9:25 窗口实测。

### 5.5 建议的折中方案（服务端定格 + 用户端展示分层）

用户的真实诉求是**「消除服务端被东财限流的风险」**，而"把打分搬到前端"只是达成它的其中一种手段，
且代价集中在 5.4 的前 4 项。**同样的诉求，还有一个不丢定格的做法：**

| 层 | 职责 | 数据来源 | 变更 |
|---|---|---|---|
| **名单层（权威）** | 打分 + 筛选 + 定格 + 落库 | 服务端全市场 clist，**9_25 只采一次** | 采样频率↓，限流压力大减 |
| **展示层（实时）** | 只刷现价/涨幅等展示字段 | **用户端本地直连 clist**（或按名单点查） | 新增前端出口 |

要点：

- 展示字段本来就由「补丁源」负责（`ModePolicy.realtime_patch`），而原补丁源 `eastmoney_realtime`
  **已被证永久失效**（5.3）⇒ 这块**本来就需要换**，让用户端接手是自然选择；
- 名单锁定后展示字段与名单无关，**用户端本地取正确价格不会破坏定格语义**；
- 服务端省掉高频轮询与点查 ⇒ 限流风险大幅下降，而 `f630`/定格/历史/审计全部保留。

> **待决策**：① 是否采纳分层方案；② 若采纳，展示层的样本口径（全市场分页 vs 按名单点查
> —— 注意点查 `ulist.np` 从浏览器特征下也需实测，服务端已死不代表浏览器端也死）。

## 六、结论速览

| 问题 | 结论 |
|---|---|
| 祖本怎么取数？ | 单文件 HTML，浏览器**直连东财 clist**，`fid=f3&po=1&pz=200`，**只取涨幅前 200**，无兜底、无后端 |
| 祖本有什么硬伤？ | 🔴 **把 `f10`（量比）当流通市值** ⇒ 11% 市值 + 32% 换手**恒满档**，43% 权重是常数；`f3` 语义标错 |
| 17% 异动因子的血缘？ | **就是 `f630`** —— 档位/默认值/权重与祖本**逐字一致** |
| `f630` 能取到吗？ | ✅ **能**。祖本时代就在用；本次实测前 200 非 0 率 53.5%、≥3 档 47.5% |
| 9/17 事故根因？ | **采集落库漏字段**（只落 8 列），不是数据源问题 |
| 用户端直连可行吗？ | ✅ **CORS 完全开放**（不带 Origin 直接 `*`），技术零障碍 |
| 用户端方案会丢什么？ | 定格 / 名单权威性 / 历史与审计 / 算法保密 / 单实现 —— 代价集中且不可逆 |
